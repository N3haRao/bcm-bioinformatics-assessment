# Task 1: GTF feature extraction and BED region mapping

Extracts transcriptome features from a GENCODE GTF into standard BED files, then
maps an external BED file (`T1.bed`) onto those features and labels each region
with the feature type it falls in.

---

## Quick start

```bash
# 1. GTF -> seven BED files 
python task1_gtf_features/scripts/01_gtf_to_bed.py \
      --gtf data/gencode.v33.annotation.gtf.gz \
      --outdir task1_gtf_features/bed_features

# 2. Map T1.bed onto those features 
python task1_gtf_features/scripts/02_map_regions_to_features.py \
      --regions data/T1.bed.txt --features task1_gtf_features/bed_features \
      --outdir task1_gtf_features/results --prefix T1

# 3. Which coordinate convention does T1 use? 
python task1_gtf_features/scripts/03_diagnose_coordinate_convention.py \
      --regions data/T1.bed.txt --features task1_gtf_features/bed_features

# 4. Enrichment, metagene and biotype interpretation
python task1_gtf_features/scripts/04_analyse_annotation.py \
      --detailed task1_gtf_features/results/T1_annotated_detailed.tsv \
      --features task1_gtf_features/bed_features \
      --out task1_gtf_features/results/T1_interpretation.txt
```

The GENCODE GTF is not committed to this repo (see
[../data/README.md](../data/README.md) for the download link). `bed_features/`
and the large detailed result files are also not committed since they are
regenerated by the commands above; only the small text reports are kept in
git so the findings are visible without re-running anything.

## Outputs

### `bed_features/` (~490 MB, not committed)

| File | Rows | Contents |
|---|---:|---|
| `genes.bed` | 60,662 | gene ID and gene name |
| `transcripts.bed` | 227,912 | transcript ID, transcript name, gene ID, gene name |
| `exons.bed` | 1,377,112 | every exon, coding or not |
| `coding_exons.bed` | 763,824 | the translated (CDS) portion of each exon |
| `five_prime_utrs.bed` | 153,280 | 5' UTR blocks |
| `three_prime_utrs.bed` | 158,588 | 3' UTR blocks |
| `introns.bed` | 1,149,200 | gaps between consecutive exons of one transcript |

Columns 1 to 6 are strict BED6 (`chrom`, `chromStart` 0-based, `chromEnd`
exclusive, `name`, `score`, `strand`). Columns 7 onward carry the same metadata
split into individual fields, so both `cut -f4` and `cut -f10` work. Every file
is coordinate sorted with chromosomes in natural order (chr1, chr2, ... chr10,
... chrX, chrY, chrM, then scaffolds).

The `name` field packs identifiers with `|`, for example
`DDX11L1|ENST00000456328.2|exon1`.

| File | Contents | Committed? |
|---|---|:---:|

## Design decisions

**GTF is 1-based inclusive, BED is 0-based half-open.** Converted once,
immediately after parsing (`start - 1`, `end` unchanged). Everything downstream
thinks purely in BED coordinates. Mixing the two conventions halfway through is
the most common source of off-by-one bugs in this kind of script.

**UTRs are derived, not copied.** GENCODE ships `UTR` lines, but we rebuild UTRs
as `exon minus CDS` and assign 5' or 3' by which side of the coding region each
leftover piece sits on, respecting strand. This works on any GTF including ones
with no UTR lines, and it lets the shipped UTR lines serve as an independent
check. That check comes out at **100.0000% agreement** across 311,868 blocks,
with zero blocks unique to either side.

**The stop codon counts as 3'UTR.** GENCODE excludes the stop codon from CDS, so
its own UTR lines place those three bases in the 3'UTR. We match that so our
output is directly comparable to the source. `--stop-codon-in-cds` flips it.

**Introns are per transcript.** An intron is the gap between two consecutive
exons of the *same* transcript. Single-exon transcripts (25,243 of them) get no
introns. Intron numbering runs in transcription order, so on a minus-strand gene
`intron1` sits at the highest coordinate.

**One label per region, by priority.** A genomic base is often several things at
once because isoforms disagree. Rather than pretend otherwise, we resolve to one
label using `CDS > 5UTR > 3UTR > noncoding exon > intron > UN` ("most
functionally specific wins") and record every class that was hit in the
`all_features_hit` column, so nothing is hidden. This matters more than it might
sound: 61,200 T1 sites hit more than one class, which is 27.9% of all mapped
sites. Any single-label annotation of this data is discarding real ambiguity, so
the extra column exists to keep that ambiguity auditable rather than invisible.

**Strand-aware by default.** T1 carries strand, and the biology here is
strand-specific. `--ignore-strand` is available; it drops UN from 29.5% to 17.8%
but almost all of the recovered sites become antisense-intronic calls, which is
exactly the kind of spurious hit strand-awareness is meant to exclude.

**Non-coding exon is derived, not read off a label.** An exon counts as
non-coding if its transcript carries no CDS anywhere. This is more reliable than
trusting `transcript_type`, because NMD transcripts are not labelled
`protein_coding` yet do have a CDS.

**Memory.** The feature set is ~4 million intervals, too much to hold at once
alongside gene names and transcript IDs. Because both the feature files and the
query file are coordinate sorted, script 02 walks them in lockstep and never
holds more than one chromosome at a time. Overlap detection is a sweep line with
a min-heap keyed on interval end, which is O(n log n) and needs no index. Whole
mapping run: about 25 seconds for 311k regions against ~4M features.

## Correctness checks performed

| Check | Result |
|---|---|
| Derived UTRs vs GENCODE's own UTR lines | 311,868 / 311,868 identical, 0 discrepancies |
| Minus-strand 5'UTR at higher coordinate than CDS | confirmed (`ENST00000426406.3`) |
| Minus-strand intron numbering counts down as coordinate rises | confirmed (`NOC2L`, 18 introns) |
| Sweep-line overlap engine vs independent brute-force scan | 700 sites, 0 mismatches |
| BED format: no zero-length or negative intervals, valid strands, sorted, consistent column count | all 7 files clean |
| 5'UTR + 3'UTR block count equals GENCODE UTR line count | 153,280 + 158,588 = 311,868 |

## A note on T1.bed

Two properties of the input file are worth knowing, both documented in
`results/coordinate_convention_diagnostic.txt`:

1. **Every row has `start == end`**, which in strict BED terms is a zero-length
   interval that can never overlap anything. These are single-nucleotide sites
   with the position written into both columns.

2. **The coordinates are 1-based, not 0-based.** This is not a guess. Read as
   1-based, 21,984 sites (7.06%) land on an annotated transcript 3' end to the
   exact base, a spike ~15x the neighbouring offsets, while the same test against
   transcript 5' ends is flat at 0.013%. Hence `--point-mode pos1` is the
   default; `--point-mode bed0` is available for genuinely 0-based files. The
   choice moves 4,801 sites.

3. **311,493 rows cover only 290,066 distinct positions.** 21,427 rows are
   duplicates. The extreme cases (up to 22 copies) all sit in the protocadherin
   clusters on chr5, which inflates the per-gene counts in the summary. Counts
   are reported per row, not per distinct site, so the deliverable stays
   row-for-row aligned with the input.
